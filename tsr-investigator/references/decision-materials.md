# 判断材料の収集

事実判定（確認 / 部分的に確認 / 反証 / 判定不能）の次に来る段階。
「この所見に対応するかどうか」を決めるための材料を揃える。

## 原則: 対応要否を判定しない

**対応するかどうかを決めるのはユーザーである。** エージェントは決めない。

判断に必要な情報のほとんどが must-gather の外にある。本番かどうか、SLA、変更凍結、運用体制、他システムとの依存、組織の方針。これらを知らないまま「不要です」と言うのは、TSR が環境を知らないまま CRITICAL を付けるのと同じ過ちになる。

やることは、**ユーザーが5分で決められるところまで材料を揃えて渡す**こと。

「対応を推奨します」も実質的な判断なので使わない。トレードオフは両論を書く。

## 今のスキルでの位置

一件ループでは、事実判定と（必要なら）外部調査のあと、記録の前に行う。

- セットアップの2問（omc / export）には足さない。
- 環境の前提は、**この段階に初めて入ったとき一度だけ**聞く。推定しない。
- 聞いた内容は `tsr-investigation.yaml` の `meta.environment` に書く。再 seed しても残す。
- 一件分の材料は `decision_brief` に書く。PDF 由来の `impact` / `recommended_actions` を上書きしない。
- `decision_brief.user_decision` はユーザー専用。エージェントは空欄のまま出し、ユーザーが決めたら記入する。`user_notes` と同じ扱い。
- 対応方針表は一次ソースではなく、ユーザーが export を頼んだときの見え方である。一件終了のたびに勝手に export しない。
- 埋まらない項目は空欄のまま「不明」と書く。推測で埋めない。

## 環境の前提（一度だけ）

`meta.environment` が無ければ、判断材料に入る前に聞く。以降は使い回す。

- このクラスタの位置づけ（本番 / ステージング / 検証 / 学習用。ユーザーの言葉で）
- 載っているワークロードの重要度と、止まったときに困る人
- 運用体制（専任がいるか、変更にどれくらいかかるか）
- 直近で予定されている変更（アップグレード、増設、本番化）

YAML のキー:

```yaml
meta:
  environment:
    role: ""
    workload_impact: ""
    ops: ""
    upcoming_changes: ""
```

聞かずに推定しない。

## 揃える材料

一件について、事実判定の後に集める。`decision_brief` のキーは英語、チャットは日本語。

### 1. 影響範囲 (`scope`)

誰が、何が、具体的に困るか。抽象的なリスク表現にしない。

- 影響を受けるノード、namespace、ワークロードを実名で挙げる
- 既に顕在化しているのか、まだ潜在的なのかを区別する
- 「クラスタが不安定になる」ではなく「worker-1 上の pod が evict される」と書く

inventory と検証で特定できたオブジェクトは名前を出す。ユーザーはそれを見て業務影響を判断する。

PDF の `impact` 欄はレポートの主張であり、ここには写さない。must-gather で確認した範囲だけを書く。

### 2. 放置した場合 (`if_ignored`)

「放置すると危険」だけでは判断できない。**何がきっかけで顕在化するか**を書く。

- 負荷が増えたとき、ノードが1台落ちたとき、再起動したとき、など
- 既に顕在化している場合は、悪化の速度がわかるなら添える
- 条件が揃わなければ顕在化しないなら、それも明記する

解説の作法にある「放置するとどうなるか」は短い予告である。ここが本体。

### 3. 対応コストとリスク (`remediation_cost`)

対応そのものが危険な場合がある。設定変更で済むのか、調達や再設計が要るのかも区別する。

OpenShift で特にコストが高い操作の例（網羅リストではない）:

| 操作 | 何が起きるか |
|------|----------------|
| KubeletConfig / MachineConfig の変更 | 対象 MCP のノードが1台ずつ drain され再起動する。全ノードに波及しうる |
| systemReserved の調整 | 上と同じ。allocatable が減り、過密なノードでは pod が押し出される |
| etcd 関連の変更 | 実施中はクォーラムに余裕がなくなる。既に不安定なら実施自体がリスク |
| オペレータの再インストール | 管理下のリソースが一時的に失われる可能性 |
| ノードの追加 / 退役 | 調達と手順が要る。即応できない |

既に不安定なクラスタでは、安定させるための変更が引き金になって落ちることがある。
ローリング再起動を伴う案を出すときは、その旨を必ず添える。

レポートの `recommended_actions` はコストを考える材料の一つであり、採用決定ではない。

### 4. 依存関係 (`depends_on` / `relieves`)

- 先に直す必要がある所見の `id` を `depends_on` へ
- これを直すと消えうる所見の `id` を `relieves` へ

TSR は所見を独立に並べるため、この情報を持っていない。調査で得た因果をここに書く。存在しない `id` を作らない。

### 5. 判断が変わる条件 (`decision_changes_if`)

ユーザーが「不要」と判断する場合、**その判断が崩れる条件**を必ず併記する。無条件の切り捨ては後で事故になる。

例:

- 「検証環境である限り不要。本番昇格時には必須」
- 「現在の負荷では顕在化しない。ワークロードを追加する前に再評価」
- 「単一 AZ 構成を許容するなら不要。冗長化要件が出たら対応」

「対応する」側でも、期限の根拠になる条件を書けるとよい。

### 6. 未確認事項 (`unconfirmed`)

判定不能だった部分、must-gather では確認できなかった部分。
「これを確認するには追加でこれが必要」まで書く。

## 記録

チャットでは材料を表で見せてよい。正本は YAML のその `id` の `decision_brief` である。

```yaml
decision_brief:
  scope: ""
  if_ignored: ""
  remediation_cost: ""
  depends_on: []
  relieves: []
  decision_changes_if: ""
  unconfirmed: ""
  user_decision: ""
```

判断の列は空欄で出す。ユーザーが決めたら `user_decision` に記入する。勝手に埋めない。

## やってはいけないこと

- 対応要否をエージェントが決めて提示する。
- 「対応を推奨します」で実質的に判断する。
- 環境の性質を推定して材料を組み立てる。
- 対応コストを書かずに対応内容だけ書く。
- 「不要」の材料を出すときに、判断が変わる条件を省略する。
- PDF の `impact` を `decision_brief.scope` にコピーする。
- セットアップの2問に環境の質問を混ぜる。
- 一件終了のたびに export する。
