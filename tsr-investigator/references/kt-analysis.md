# 所見の切り分け: IS / IS-NOT

Kepner-Tregoe の Problem Analysis を must-gather 調査に合わせたもの。
一件の所見について、原因候補を絞るときに読む。

レポート内部の矛盾（所見同士が同時に成立しにくいか）は、must-gather を開く前の一覧ステップの仕事である。手順は `SKILL.md` にあり、ここでは繰り返さない。

## なぜ使うか

TSR は所見をフラットに並べ、それぞれに原因らしきものを添える。
そのまま受け取ると、レポートが提示した原因に思考が固定される（アンカリング）。
TSR の因果主張は仮説である。

IS / IS-NOT の要点は、起きていることだけでなく「起きていてもおかしくないのに、起きていないこと」を並べるところにある。後者が原因候補を消す。片方だけでは、どんな雑な仮説でも成立してしまう。

## 今のスキルでの位置

一件ループの「切り分けと検証方針」で使う。検証手順書ではない。
ユーザー向けの言葉は「起きていること / 起きていないこと」。IS/IS-NOT はエージェント内部の呼び方である。

- **完成した表を検証の前に要求しない。** 空欄は失敗ではなく、次に合意するコマンドである。
- **最初に書くこと** はカタログ（`tsr-inventory.yaml`）と、その所見の YAML に既にある `evidence` だけ。レポートの文章を写さない。チャットではファイル名より先に、その意味を日常語で言う。
- レポートが挙げた原因は、並列の一候補として扱う。筆頭に置かない。
- 表そのものはチャットに出す。YAML に IS/IS-NOT 用のフィールドは足さない。結論だけ `evidence` / `interpretation` / `next_actions` に書く。

## 手順

### 1. IS を4側面で書く

must-gather（または inventory）で確認できた事実だけを書く。まだ見ていないセルは空のまま残す。

| 側面 | 問い |
|------|------|
| 何が (WHAT) | どのコンポーネント/オブジェクトに、どういう異常が出ているか |
| どこで (WHERE) | どのノード、どの namespace、どのディスク/インターフェース |
| いつ (WHEN) | 初出はいつか。継続的か断続的か。周期性はあるか |
| どの程度 (EXTENT) | 件数、割合、基準値との倍率。影響範囲は全体の何割か |

WHERE の第一候補は inventory の `namespace_index` と `plugins[].nodes`。無いと言う前に両方のプラグインを見る。

### 2. IS-NOT を対にして書く

各側面について「同じ条件なら起きていてもおかしくないのに、実際には起きていないこと」を探す。ここが本体であり、飛ばすと KT ではない。

例: etcd の fsync が遅い、という所見

| 側面 | IS | IS-NOT (could be, but isn't) |
|------|----|------------------------------|
| WHAT | etcd の書き込みが遅い | 同じディスクを使う他プロセスは遅くない? |
| WHERE | master-1 | master-0 と master-2 は? 3台とも同程度か、1台だけか |
| WHEN | 採取時点で継続 | いつからか。ある変更以前は正常だったか |
| EXTENT | 推奨の約48倍 | 全時間帯で48倍か、スパイクの分位点か |

IS-NOT が埋まらない場合は、それ自体が「まだ何もわかっていない」というサインである。無理に埋めず、埋めるための調査を次のアクションにする。

WHEN が空のままで前後関係や引き金を見たいときは、常用しない時系列再構成を提案する。`references/timeline.md`。

### 3. 差分から原因候補を出す

IS と IS-NOT の**違いは何か**、その違いが**いつ持ち込まれたか**を問う。
「master-1 だけ遅く、master-0 は正常」なら、両者の差（ディスク、負荷、同居 pod、MachineConfig）が候補になる。
「3台とも同程度に遅い」なら、個体差ではなく共通基盤が候補になる。この切り分けだけで範囲が桁で変わる。

複数原因の併存を疑うときは、判定を `partial` にしてよい。単一原因にまとめない。

### 4. 候補を IS と IS-NOT の両方で検証する

各候補について問う。

> この原因が正しいとして、**IS を説明できるか。そして IS-NOT も説明できるか**。

IS だけ説明できて IS-NOT を説明できない候補は、たいてい間違っている。
「ストレージ全体が遅い」は、master-1 だけが遅いという IS-NOT を説明できない。この時点で棄却できる。

説明できない部分が残る場合は、候補を棄却するか、複数原因の併存を疑う。

候補を棄却しても、所見そのものの `status` は自動で `contradicted` にしない。棄却したのは原因仮説であり、症状の有無とは別である。

## テスト可能性スクリーン

must-gather は採取時点で凍結したスナップショットであり、実験ができない。
検証方針を出す前に、候補ごとに次を判定する。

**この仮説は、手元のデータで棄却可能か**

| 判定 | 対応 |
|------|------|
| 棄却可能 | 通常どおり検証方針を提示し、合意を得て実行 |
| 棄却不能 | その旨を明示し、追加採取または live 確認を `next_actions` に書く。YAML `status` は必要なら `inconclusive` |

棄却不能な仮説を、それらしい傍証で「たぶんこれ」と結論づけない。何を採取すれば判定できるかを具体的に書いて渡す。

config の `tools.omc` が `skip` なら omc を提案しない。パスは inventory と `references/must-gather-map.md` を正とする。

## やってはいけないこと

- IS だけ書いて原因候補に進む。IS-NOT がない分析は KT ではない。
- レポートが挙げた原因を候補リストの筆頭に置く。
- 全所見の IS / IS-NOT を自動で埋める。
- 相関を因果として扱う。時間的に近接していることは、それだけでは根拠にならない。
- 単一原因に強引にまとめる。
- 手元で棄却できない仮説を、作文で閉じる。
